# Защита CI

CI проверяет секреты в коде и в истории Git. Если Gitleaks находит похожий
на токен, пароль или приватный ключ фрагмент, job `Secret scan` завершается
ошибкой и PR нельзя считать проверенным.

Проверка запускается при каждом `push`, `pull_request` и вручную из вкладки
Actions. Для сканирования истории checkout получает все коммиты (`fetch-depth: 0`).

## Почему workflow не публикует отчёт

Проверка имеет только разрешения `contents: read` и `pull-requests: read`.
Второе нужно Gitleaks, чтобы получить список коммитов проверяемого PR. У неё
нет права писать комментарии к PR. Также отключены summary и загрузка artifact:
потенциальный фрагмент секрета не должен становиться новым доступным файлом или
комментарием. `GITHUB_TOKEN` передаётся самому Action только для служебных
запросов с теми же правами только на чтение.

Если проверка сработала, не копируйте находку в issue, PR или чат. Нужно:

1. Сразу отозвать или перевыпустить скомпрометированный ключ в исходном сервисе.
2. Удалить его из рабочей копии и из коммита.
3. Если секрет уже был опубликован, обсудить с командой очистку истории Git.
4. Запустить CI ещё раз.

Сканер уменьшает риск случайного раскрытия, но не доказывает отсутствие всех
возможных секретов. Реальные токены сохраняются только в Secrets GitHub или в
локальном `.env`, который исключён через `.gitignore`.

## Защита зависимостей CI

Все Actions в `.github/workflows/ci.yml`, `security.yml` и
`container-security.yml` указаны полными SHA
коммитов. Это означает, что внешняя Action не изменится незаметно под тем же
тегом. Комментарий после SHA сохраняет читаемое имя версии для будущего обновления.

## Сканирование Docker-образов

Workflow `Container security` собирает backend- и frontend-образы и проверяет
их Trivy. Проверка PR завершается ошибкой, если в Linux-пакетах образа
найдена уязвимость уровня `HIGH` или `CRITICAL`, для которой уже существует
исправление.

Неисправимые на данный момент уязвимости не блокируют PR: команда не может
обновить пакет до ещё не выпущенной версии. При появлении исправления
следующий запуск начнёт считать находку блокирующей.

Эта проверка отвечает только за системный слой образов. Python- и npm-зависимости
проверяются отдельными SCA-job, чтобы правила и ошибки каждой проверки были понятны.
