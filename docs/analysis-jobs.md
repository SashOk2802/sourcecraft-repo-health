# Жизненный цикл запусков анализа

## Состояния

Каждый запуск имеет безопасный идентификатор анализа и проходит строго определённые
состояния:

~~~text
queued -> running -> completed
                  -> partial
                  -> failed
~~~

- queued: backend принял запуск и ожидает обработчик.
- running: обработчик уже собирает данные и рассчитывает категории.
- completed: все применимые категории получили итоговый результат.
- partial: часть применимых категорий недоступна или завершилась с ошибкой; отчёт всё равно сохранён.
- failed: запустить анализ или сохранить его снимок не удалось; отчёта для этого ID нет.

Запрещены прямой переход queued в terminal-состояние, повторный старт и изменение
terminal-состояния. В failed обязательно сохраняются машинный код и безопасное
сообщение ошибки без токенов и других секретов.

## Хранение

Миграция Alembic создаёт таблицу `analysis_jobs`. `PostgresAnalysisJobStore`
хранит в ней ID запуска, ID репозитория, статус, временные метки и, для failed,
описание ошибки. Таблица `analysis_snapshots` остаётся отдельным неизменяемым
хранилищем готовых отчётов.

Для PostgreSQL сохранение снимка и terminal-статуса выполняется одной транзакцией:
после completed или partial нельзя получить отчёт при ещё работающем задании.

## HTTP-запуск и обработчик

`POST /api/v1/repositories/{repository_id}/analyses` создаёт queued-задание и
возвращает клиенту его ID со статусом 202. `GET /api/v1/analyses/{analysis_id}`
даёт frontend возможность опрашивать queued, running и terminal-состояния.

`InProcessAnalysisDispatcher` — минимальный обработчик для приложения FastAPI.
Он получает контекст репозитория и зарегистрированные анализаторы через внедрённые
зависимости, создаёт фоновую задачу и передаёт её `AnalysisExecutionService`.
Тот переводит задание в running, вызывает анализаторы, сохраняет снимок и отмечает
completed или partial. При неожиданной ошибке он отмечает failed.

Стандартный `create_app()` не подключает dispatcher и корректно отвечает 503
на POST. До реальной интеграции нужны два компонента:

1. `RepositoryContextResolver`, который проверяет доступ пользователя и
   получает из SourceCraft репозиторий, актуальный commit и период анализа.
2. Provider анализаторов, который создаёт зарегистрированные реализации
   security, cicd, documentation, activity, issues и code_health.

Это защищает API от запуска пустого анализа. После появления SourceCraft-клиента
те же зависимости можно передать в `InProcessAnalysisDispatcher` без изменения
HTTP-контракта. При переходе к отдельному worker или очереди нужно сохранить
этот контракт и восстановление незавершённых заданий после аварийного завершения
процесса.
