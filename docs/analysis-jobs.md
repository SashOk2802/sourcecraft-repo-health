# Жизненный цикл запусков анализа

## Состояния

Каждый запуск имеет безопасный идентификатор анализа и проходит строго определённые
состояния:

~~~text
queued -> running -> completed
                  -> partial
                  -> failed
~~~

- queued: backend принял запуск и ожидает обработчик.
- running: обработчик уже собирает данные и рассчитывает категории.
- completed: все применимые категории получили итоговый результат.
- partial: часть применимых категорий недоступна или завершилась с ошибкой; отчёт всё равно сохранён.
- failed: запустить анализ или сохранить его снимок не удалось; отчёта для этого ID нет.

Запрещены прямой переход queued в terminal-состояние, повторный старт и изменение
terminal-состояния. В failed обязательно сохраняются машинный код и безопасное
сообщение ошибки без токенов и других секретов.

## Хранение

PostgresAnalysisJobStore создаёт таблицу analysis_jobs. Она хранит ID запуска,
ID репозитория, статус, временные метки и, для failed, описание ошибки. Таблица
analysis_snapshots остаётся отдельным неизменяемым хранилищем готовых отчётов.

## Как это подключится к API

Будущий POST запуска анализа создаст queued-задание, передаст ID в фоновый
обработчик, а затем вернёт клиенту этот ID. Обработчик переводит задание в
running, вызывает анализаторы, сохраняет снимок и отмечает completed или partial.
При неожиданной ошибке он отмечает failed.

Пока нет подтверждённого SourceCraft-слоя и реальных подключённых анализаторов,
этот модуль не запускает задания сам. Он подготовлен для безопасного подключения
к ним без изменения формулы Score.
