# Жизненный цикл запусков анализа

## Состояния

Каждый запуск имеет безопасный идентификатор анализа и проходит строго определённые
состояния:

~~~text
queued -> running -> completed
                  -> partial
                  -> failed
~~~

- queued: backend принял запуск и ожидает обработчик.
- running: обработчик уже собирает данные и рассчитывает категории.
- completed: все применимые категории получили итоговый результат.
- partial: часть применимых категорий недоступна или завершилась с ошибкой; отчёт всё равно сохранён.
- failed: запустить анализ или сохранить его снимок не удалось; отчёта для этого ID нет.

В обычной работе запрещены прямой переход queued в terminal-состояние, повторный
старт и изменение terminal-состояния. В failed обязательно сохраняются машинный
код и безопасное сообщение ошибки без токенов и других секретов.

Исключение — восстановление после остановки in-process worker. Каждый
dispatcher получает собственный `worker_id` и регулярно продлевает его lease.
При старте новый dispatcher завершает с кодом `worker_interrupted` только
queued и running задания владельцев с просроченным heartbeat. Задание с
актуальным heartbeat другого экземпляра не изменяется: rolling deploy или
второй процесс API не прерывает работающий анализ. Проверка lease повторяется
в самом SQL-обновлении, поэтому heartbeat, пришедший параллельно с recovery,
сохраняет задание.

## Хранение

Миграции Alembic создают таблицы `analysis_jobs` и
`analysis_worker_leases`. `PostgresAnalysisJobStore` хранит в задании ID
запуска, ID репозитория, статус, временные метки, владельца worker и, для
failed, описание ошибки. Таблица `analysis_snapshots` остаётся отдельным
неизменяемым хранилищем готовых отчётов.

Для PostgreSQL сохранение снимка и terminal-статуса выполняется одной транзакцией:
после completed или partial нельзя получить отчёт при ещё работающем задании.

## HTTP-запуск и обработчик

`POST /api/v1/repositories/{repository_id}/analyses` принимает запрос только
при настроенной аутентификации. HTTP-слой получает проверенный
`AnalysisPrincipal` и передаёт его в dispatcher; в principal нет токенов и иных
секретов. `RepositoryContextResolver` обязан проверить этим principal доступ к
репозиторию до создания задания. Если доступа нет, endpoint отвечает `403`.

`GET /api/v1/analyses/{analysis_id}` даёт frontend возможность опрашивать
queued, running и terminal-состояния.

`InProcessAnalysisDispatcher` — минимальный обработчик для одного процесса
FastAPI. Он получает авторизованный контекст репозитория и зарегистрированные
анализаторы через внедрённые зависимости, создаёт фоновую задачу и передаёт её
`AnalysisExecutionService`. Тот переводит задание в running, вызывает
синхронный `run_analysis` через `asyncio.to_thread`, сохраняет снимок и
отмечает completed или partial. Поэтому длительная синхронная категория не
блокирует event loop и endpoint состояния продолжает отвечать.

Стандартный `create_app()` не подключает ни dispatcher, ни аутентификацию и
корректно отвечает `503` на POST. До реальной интеграции нужны три компонента:

1. Provider аутентифицированного principal из пользовательской сессии.
2. `RepositoryContextResolver`, который по principal проверяет доступ и
   получает из SourceCraft репозиторий, актуальный commit и период анализа.
3. Provider анализаторов, который создаёт зарегистрированные реализации
   security, cicd, documentation, activity, issues и code_health.

Это защищает API от запуска приватного репозитория сервисным токеном от имени
произвольного клиента. При переходе к отдельному worker или очереди нужно
сохранить HTTP-контракт, передавать проверенный principal или безопасную ссылку
на него и заменить recovery на requeue с устойчивой доставкой.
