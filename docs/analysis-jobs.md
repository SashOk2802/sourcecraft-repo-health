# Жизненный цикл запусков анализа

## Состояния

Каждый запуск имеет безопасный идентификатор анализа и проходит строго определённые
состояния:

~~~text
queued -> running -> completed
                  -> partial
                  -> failed
~~~

- queued: backend принял запуск и ожидает обработчик.
- running: обработчик уже собирает данные и рассчитывает категории.
- completed: все применимые категории получили итоговый результат.
- partial: часть применимых категорий недоступна или завершилась с ошибкой; отчёт всё равно сохранён.
- failed: запустить анализ или сохранить его снимок не удалось; отчёта для этого ID нет.

В обычной работе запрещены прямой переход queued в terminal-состояние, повторный
старт и изменение terminal-состояния. В failed обязательно сохраняются машинный
код и безопасное сообщение ошибки без токенов и других секретов.

Исключение — восстановление после остановки in-process worker. Каждый
dispatcher получает собственный `worker_id` и регулярно продлевает его lease.
При старте и при каждом следующем heartbeat dispatcher завершает с кодом
`worker_interrupted` только queued и running задания владельцев с просроченным
heartbeat. Задание с актуальным heartbeat другого экземпляра не изменяется:
rolling deploy или второй процесс API не прерывает работающий анализ. Проверка
lease повторяется в самом SQL-обновлении, поэтому heartbeat, пришедший
параллельно с recovery, сохраняет задание.

Задания старой версии не имеют `worker_id`. При миграции создаётся deadline
на пять минут вперёд. До него ownerless-задания не изменяются: старый worker
успевает завершить уже начатую работу. После deadline живой dispatcher завершит
оставшиеся ownerless-задания как `worker_interrupted`. При развёртывании нужно
сначала убрать старую версию из балансировки и дать ей закончить текущие
запуски, затем применить миграции и запустить новую версию.

## Хранение

Миграции Alembic создают таблицы `analysis_jobs`,
`analysis_worker_leases` и `analysis_job_recovery_state`. Последняя хранит
deadline для единовременного drain ownerless-заданий после миграции.
`PostgresAnalysisJobStore` хранит в задании ID запуска, ID репозитория,
subject сессии инициатора (`owner_subject`), статус, временные метки,
владельца worker и, для failed, описание ошибки. Миграция `20260925_04`
добавляет `owner_subject`. Строка без subject по HTTP не читается: старые
задания остаются в таблице, но статус и отчёт по ним отвечают `404`.
Таблица `analysis_snapshots` владельца не хранит. Доступ к снимку решает
строка задания. Снимок остаётся отдельным неизменяемым хранилищем готового
отчёта.

Для PostgreSQL сохранение снимка и terminal-статуса выполняется одной транзакцией:
после completed или partial нельзя получить отчёт при ещё работающем задании.

## HTTP-запуск и обработчик

`POST /api/v1/repositories/{repository_id}/analyses` принимает запрос только
при настроенной аутентификации. HTTP-слой получает проверенный
`AnalysisPrincipal` и передаёт его в dispatcher; в principal нет токенов и иных
секретов: subject сессии Яндекс ID. Planner на сервере проверяет, есть ли у
этого subject личное подключение SourceCraft. При наличии подключения он
выпускает короткоживущий зашифрованный lease и проверяет доступ к репозиторию
личным PAT. Браузер передаёт только `repository_id`. Нет сессии — `401` с
текстом `Authentication required.`. Отклонённый сохранённый PAT — `401` с
текстом `SourceCraft rejected the token.`. Нет подключения и нет доступа через
public fallback — `409`. Ограничение частоты — `429`, непригодный снимок —
`502`, недоступный SourceCraft или повреждённое подключение — `503`.

`GET /api/v1/analyses/{analysis_id}` даёт frontend возможность опрашивать
queued, running и terminal-состояния.

`InProcessAnalysisDispatcher` — минимальный обработчик для одного процесса
FastAPI. Он получает авторизованный контекст репозитория и зарегистрированные
анализаторы через внедрённые зависимости, создаёт фоновую задачу и передаёт её
`AnalysisExecutionService`. Тот переводит задание в running, вызывает
синхронный `run_analysis` через `asyncio.to_thread`, сохраняет снимок и
отмечает completed или partial. Поэтому длительная синхронная категория не
блокирует event loop и endpoint состояния продолжает отвечать.

`create_app()` без dispatcher и без аутентификации отвечает `503`. Рабочий
процесс вызывает `create_app()` и выбирает personal/public режим только по
server-side состоянию. Сервисный токен public fallback не открывает
private/internal, даже если сам имеет к ним доступ. `create_sourcecraft_app()`
остаётся отдельной тестовой сборкой старого Bearer-пути и входом процесса не
является. Жизненный цикл FastAPI сам вызывает `dispatcher.start()` и
`dispatcher.close()`.

Principal — это `user.id` сессии Яндекс ID. Personal planner сверяет владельца
lease с этим subject, затем читает `GET /repos/id:{repository_id}` и commit
ветки по умолчанию: `filter` по имени ветки и не больше 100 страниц. Период
анализа — 180 дней. Activity, Issues и CI/CD открывают личный API-клиент только
на время сбора. Documentation и Code health используют один ограниченный
временный Git-workspace. Security получает только безопасный AppSec snapshot.
Plaintext PAT не сохраняется в principal, context, job, отчёт или PostgreSQL.

После рестарта незавершённое personal-задание завершается с
`worker_interrupted`: worker не восстанавливает его через сохранённый PAT.
При переходе к отдельному worker или очереди нужно сохранить HTTP-контракт,
передавать проверенный principal или безопасную ссылку на него и заменить
recovery на requeue с устойчивой доставкой.
