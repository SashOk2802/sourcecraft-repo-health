# Как формируются рекомендации

Рекомендации — детерминированные правила по собранным фактам: одинаковые данные дают одинаковый список. AI не используется. Код — в анализаторах категорий (`backend/app/analyzers/`), сборка — `backend/app/analysis/runner.py`.

## Из чего состоит рекомендация

Каждая рекомендация — запись `Recommendation` из `backend/app/contracts.py`. Поля покрывают п. 3.3 ТЗ:

| Поле | Что это | Пункт ТЗ |
| --- | --- | --- |
| `problem` | обнаруженная проблема с числами из фактов | обнаруженная проблема |
| `rationale` | почему это важно | почему она важна |
| `evidence` | ссылки на факты: файл и строка, запуск CI, страница AppSec, задача | на каких фактах основан вывод |
| `action` | что сделать | рекомендуемое действие |
| `priority` | `P0`–`P3` | приоритет исправления |
| `expectedEffect`, `expectedScoreDelta` | что изменится и насколько вырастет оценка | ожидаемое влияние |
| `code` | стабильный код правила, например `issues-triage-stale` | — |

## Правила

1. **Только по измеренным данным.** Рекомендация появляется, только если метрика посчитана. Отсутствие данных не порождает рекомендаций вида «почините то, чего мы не видим»: оно показывается статусом категории.
2. **Приоритет задаёт правило, а не вес категории:**
   - `P0` — критично, исправлять немедленно: открытая критическая уязвимость AppSec. Подтверждённая критическая уязвимость ещё и ограничивает Score значением 60;
   - `P1` — серьёзная проблема: нет README, проект не обновлялся больше 90 дней, больше 20% задач брошены, успешность CI ниже 80%, два и больше FIXME;
   - `P2` — заметная проблема: нет лицензии, CONTRIBUTING или инструкций запуска, очередь задач растёт, MR не сливаются;
   - `P3` — гигиена и профилактика: CODEOWNERS, много TODO, давно не было релиза.
3. **Без дублей.** Если два правила выдали рекомендацию с одним кодом, остаётся та, у которой приоритет выше.
4. **Порядок.** Сначала по приоритету (`P0` → `P3`), внутри приоритета — по коду правила. Порядок стабилен между запусками.
5. **Ожидаемое влияние.** `expectedScoreDelta` заполняется там, где прирост считается точно: насколько вырастет оценка категории после исправления. Для Documentation это штраф за недостающий файл. Для Code health — разница оценки категории до и после устранения меток. Вклад в итоговый Score — этот прирост, умноженный на долю категории в Score: `effectiveWeight / 100` в отчёте. Где точный прирост посчитать нельзя (CI, Issues, Activity, Security), поле `null`, а ожидаемый эффект описан словами.
6. **Доказательства — только проверяемые.** Ссылка ведёт на конкретный объект SourceCraft: строку файла на зафиксированном коммите, упавший запуск CI, страницу SAST, SCA или Secrets, задачу. Если ссылку построить нельзя, в отчёте остаётся текстовое описание факта.

## Правила по категориям

| Категория | Рекомендации и условия | Подробно |
| --- | --- | --- |
| Security | `P0`–`P3` по наивысшей критичности открытых находок AppSec | [security-analyzer.md](security-analyzer.md) |
| CI/CD | `cicd-investigate-failed-runs`: `P1` при успешности ниже 80%, иначе `P2` | [scoring-methodology.md § 4.1](scoring-methodology.md) |
| Documentation | `doc_missing_*`: README `P1`; CONTRIBUTING, LICENSE, инструкции запуска `P2`; CODEOWNERS `P3` | [scoring-methodology.md § 4.4](scoring-methodology.md) |
| Activity | `activity-stale-repository` `P1`, `activity-mr-not-merged` и `activity-no-commits-in-period` `P2`, `activity-no-recent-release` `P3` | [scoring-methodology.md § 3.3](scoring-methodology.md) |
| Issues | `issues-triage-stale` `P1`, `issues-backlog-growing` `P2`, `issues-aging-watch` `P3` | [scoring-methodology.md § 2.4](scoring-methodology.md) |
| Code health | `code_health_resolve_fixme`: `P1` от двух FIXME, иначе `P2`; `code_health_clear_todos` `P3` | [scoring-methodology.md § 4.3](scoring-methodology.md) |

## Пример из отчёта

~~~text
P1 · Добавьте README.md с описанием архитектуры и назначения проекта.
Проблема: В репозитории проекта отсутствует или не заполнен README.md.
Почему важно: Качественная техническая документация и прозрачные правила снижают TTM и упрощают онбординг.
Ожидаемое влияние: expectedScoreDelta = 20 — оценка «Документации» вырастет на 20 баллов.
При всех шести измеренных категориях доля Документации 20%, то есть итоговый Score +4.
~~~

Тот же список с приоритетами, фактами и ожидаемым влиянием попадает в Markdown-выгрузку (`GET /api/v1/analyses/{id}/report.md`) и в PDF со страницы отчёта.
