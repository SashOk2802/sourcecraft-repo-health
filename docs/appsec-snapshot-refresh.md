# Регулярное обновление AppSec snapshot

Security-анализ читает только обезличенные snapshots из read-only каталога. Он не
запускает SourceCraft CLI и не получает IAM-сессию пользователя. Чтобы повторный
анализ использовал актуальные AppSec-данные, отдельный операторский процесс должен
обновлять snapshots чаще, чем истекает
`SOURCECRAFT_APPSEC_SNAPSHOT_MAX_AGE_SECONDS`.

## Файл публичных репозиториев

Создайте UTF-8 файл вне репозитория и вне каталога, доступного web-приложению:

```text
# По одному публичному репозиторию в строке
OWNER/REPOSITORY
ANOTHER_OWNER/ANOTHER_REPOSITORY
```

Пустые строки и строки, начинающиеся с `#`, пропускаются. Повторы удаляются до
запросов. Путь к файлу должен быть абсолютным. За один запуск принимается не
больше 1000 репозиториев, а размер файла ограничен 128 КиБ.

Не добавляйте этот файл в Git. Для private/internal репозиториев используйте
персональный анализ: общий refresh-процесс предназначен только для явно выбранных
публичных проектов.

## Команда обновления

Сначала выполните `src auth login` для обычного API и отдельного read-only AppSec
профиля, как описано в [настройке AppSec-поставщика](sourcecraft-appsec-api.md).
Затем запустите:

```sh
python scripts/export_sourcecraft_appsec_snapshot.py \
  --repositories-file /absolute/path/appsec-public-repositories.txt \
  --output-dir "$SOURCECRAFT_APPSEC_SNAPSHOT_HOST_DIR" \
  --reader-gid "$SOURCECRAFT_APPSEC_SNAPSHOT_READER_GID" \
  --appsec-env AppSecRead
```

Пакетный режим требует `--appsec-env`: ограниченный CLI-зонд не доказывает
полноту и не подходит для регулярной production-оценки. Репозитории обрабатываются
последовательно, чтобы не создавать всплеск запросов к SourceCraft и не запускать
конкурирующее обновление одной IAM-сессии.

Перед записью каждого snapshot exporter заново получает metadata репозитория через
SourceCraft и требует точное `visibility=public`. Строка из файла не может включить
private/internal репозиторий в общий refresh даже при наличии более широких прав у
локальной IAM-сессии. Фиксированная CLI-проекция передаёт Python-процессу только
`id` и `visibility`, без clone URL и остальных metadata.

Каждый snapshot записывается атомарно. Сбой одного репозитория не прерывает
остальные обновления и не повреждает его предыдущий файл. Команда возвращает
ненулевой exit code, если хотя бы один экспорт не удался. В stdout/stderr выводятся
только количества успешных и неуспешных обновлений: slug, пути SourceCraft,
содержимое findings и ошибки CLI не печатаются.

## Расписание

Если TTL равен 3600 секундам, запускайте команду, например, каждые 30 минут.
Конкретный cron или systemd timer храните в инфраструктурном репозитории стенда:
ему нужны путь к локальному `src`, каталог snapshot и действующая IAM-сессия.

После каждого запуска проверяйте exit code. Старый snapshot остаётся на месте,
но после истечения TTL backend честно вернёт `unavailable`, пока безопасное
обновление снова не завершится успешно.
