# Один запрос на согласование: пороги Code health (V.1 + V.2)

> Статус: **PENDING_APPROVAL** — ожидает решения владельца методики.
> Вопросы ревью V.1 и V.2 объединены в одно сообщение, потому что это решения
> одного класса: корректность выбранных порогов. Оба значения сейчас только
> задокументированы и покрыты тестами — независимого подтверждения нет.
> Тесты и документация доказывают стабильность поведения и его видимость для
> ревьюеров, но не корректность самих чисел.

## Контекст

Оба порога реализованы в [`backend/app/analyzers/code_health.py`](../backend/app/analyzers/code_health.py)
(`_density_penalty()`, `FIXME_CRITICAL_COUNT = 2`) и описаны в
[`docs/scoring-methodology.md`](../docs/scoring-methodology.md) §5.2 («Правило
малых репозиториев» и «Порог „критичного FIXME“»). Обе записи помечены
`PENDING_APPROVAL` до вашего решения.

## Вопрос 1 (ревью V.1) — правило малых репозиториев

Должен ли репозиторий с `total_files <= 5` и одним FIXME получать **0** баллов
по категории Code health?

Текущее поведение: `penalty = (fixmes * 5 + todos * 1) / total_files * 100`
(`_density_penalty()`), при одном FIXME и `total_files <= 5` penalty ≥ 100,
score = 0. Это следствие нормировки на число файлов, а не отдельное правило.

Фактическая кривая (1 FIXME, без TODO, измерено регрессионным тестом
`test_code_health_small_repo_single_marker_density_semantics`):

| total_files | FIXME | Score |
| ---: | ---: | ---: |
| 1 | 1 | 0.0 |
| 3 | 1 | 0.0 |
| 6 | 1 | 16.67 |
| 100 | 1 | 95.0 |

## Вопрос 2 (ревью V.2) — порог «критичного FIXME»

Должен ли `fixmes >= 2` оставаться точной границей эскалации до **P1**, а
единичный FIXME — **P2**?

Текущее поведение: `FIXME_CRITICAL_COUNT = 2` в `code_health.py`;
задокументировано в `scoring-methodology.md` §5.2. Альтернатива: одиночный
FIXME тоже трактуется как критический (P1), либо порог выше 2.

## Формат ответа

Один тикет на оба вопроса (не два параллельных треда). После согласования
маркеры `PENDING_APPROVAL` в `scoring-methodology.md` снимаются, а решение
фиксируется в §5.2.
