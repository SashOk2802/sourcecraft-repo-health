# Один запрос на согласование: пороги Code health (V.1 + V.2)

> Статус: **APPROVED** — решение владельца методики принято (ревью V.1 + V.2).
> Вопросы ревью V.1 и V.2 объединены в одно сообщение, потому что это решения
> одного класса: корректность выбранных порогов. Оба значения задокументированы
> и зафиксированы регрессионными тестами: кривую малых репозиториев проверяет
> `test_code_health_small_repo_single_marker_density_semantics`, границу
> `FIXME_CRITICAL_COUNT = 2` — `test_code_health_fixme_critical_count_boundary`.
> Тесты и документация доказывают стабильность поведения и его видимость для
> ревьюеров, но не корректность самих чисел — независимого подтверждения нет.

## Контекст

Оба порога реализованы в [`backend/app/analyzers/code_health.py`](../backend/app/analyzers/code_health.py)
(`_density_penalty()`, `FIXME_CRITICAL_COUNT = 2`) и описаны в
[`docs/scoring-methodology.md`](../docs/scoring-methodology.md) §4.3 («Правило
малых репозиториев» и «Порог „критичного FIXME“»). Записи были помечены
`PENDING_APPROVAL`; маркеры сняты после согласования (решение ниже).

## Вопрос 1 (ревью V.1) — правило малых репозиториев

Должен ли репозиторий с `total_files <= 5` и одним FIXME получать **0** баллов
по категории Code health?

Текущее поведение: `penalty = (fixmes * 5 + todos * 1) / total_files * 100`
(`_density_penalty()`), при одном FIXME и `total_files <= 5` penalty ≥ 100,
score = 0. Это следствие нормировки на число файлов, а не отдельное правило.

Фактическая кривая (1 FIXME, без TODO, измерено регрессионным тестом
`test_code_health_small_repo_single_marker_density_semantics`):

| total_files | FIXME | Score |
| ---: | ---: | ---: |
| 1 | 1 | 0.0 |
| 3 | 1 | 0.0 |
| 6 | 1 | 16.67 |
| 100 | 1 | 95.0 |

## Вопрос 2 (ревью V.2) — порог «критичного FIXME»

Должен ли `fixmes >= 2` оставаться точной границей эскалации до **P1**, а
единичный FIXME — **P2**?

Текущее поведение: `FIXME_CRITICAL_COUNT = 2` в `code_health.py`;
задокументировано в `scoring-methodology.md` §4.3 и зафиксировано регрессионным
тестом `test_code_health_fixme_critical_count_boundary` (P2 при одном FIXME,
P1 от двух включительно). Альтернатива: одиночный FIXME тоже трактуется как
критический (P1), либо порог выше 2.

## Решение владельца методики

1. **Вопрос 1 (правило малых репозиториев) — утверждено.** Категория Code health
   обнуляется при одиночном FIXME и `total_files <= 5` (одинокий TODO — при
   `total_files = 1`). Это следствие нормировки плотности; новые пороги не вводятся.
2. **Вопрос 2 (порог «критичного FIXME») — утверждено.** `FIXME_CRITICAL_COUNT = 2`
   остаётся точной границей: единичный FIXME — P2, от двух включительно — P1.

Маркеры `PENDING_APPROVAL` в `scoring-methodology.md` сняты, решение
зафиксировано в §4.3.

## Формат ответа

Один тикет на оба вопроса (не два параллельных треда) — итог зафиксирован в
разделе «Решение владельца методики» выше.
