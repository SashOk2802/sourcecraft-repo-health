# Текущий этап Security-анализатора

Модуль `backend/app/analyzers/security.py` преобразует предоставленные AppSec-данные
в общий `CategoryResult`. Это промежуточный слой: сетевого поставщика, автоматического
подключения в рабочий запуск и числовой оценки безопасности в этом PR нет.
Общие контракты и формула итогового Score не меняются.

## Вход и результат

Поставщик — синхронная функция `RepositoryRef → SecurityFacts`. Ей передаётся
репозиторий текущего запуска. `SecurityFacts` содержит `payload` (объект, список
или `None`) и необязательную непустую строку `source_error`. Данные вместе с ошибкой
не допускаются. Эти проверки действуют и при прямом создании `SecurityFacts`,
и через `build_facts`.

| Вход | Статус категории | Причина | Метрика доступности |
| --- | --- | --- | --- |
| `payload=None`, ошибки нет | `unavailable` | `appsec_unavailable` | `unavailable` |
| Объект или список, включая пустые | `insufficient_sample` | `security_scoring_not_configured` | `received` |
| `source_error` задан | `error` | `appsec_source_error` | `error` |
| Поставщик выбросил исключение или вернул не `SecurityFacts` | `error` | `appsec_source_error` | `error` |

Во всех случаях `score` и `normalized_score` равны `None`, рекомендации пусты.
Security не участвует в числовом Score и не увеличивает покрытие измеренных
категорий. Остальные категории продолжают рассчитываться.

`null` не объясняет причину отсутствия результатов и не означает ноль уязвимостей.
Пустой или непустой объект/список подтверждает только получение ответа.
Схема findings, полнота выборки, завершение сканирования и соответствие коммиту
здесь ещё не проверяются. Будущий поставщик обязан отличать результат AppSec
от ошибочного ответа источника и настроить ограничения сетевого ожидания.

Существующий вспомогательный `appsec_payload_status` сохраняет `measured` для
объекта/списка как статус получения данных. Это не статус готовой категории:
`evaluate` возвращает для такого ответа `insufficient_sample` без балла.

## Подключение к общему запуску

Фабрика `make_analyzer(provider)` возвращает функцию `AnalysisContext → CategoryResult`,
которую можно передать в `AnalyzerRegistration("security", ...)`. Поставщик вызывается
для каждого запуска; факты предыдущего репозитория не кешируются внутри анализатора.
Фабрика не устанавливает CLI, не получает токены и не выполняет сетевые запросы сама.

Реальный поставщик для web-сервиса, его авторизация и рабочая регистрация
анализатора — следующий этап после подтверждения стабильного контракта AppSec.
Непустые синтетические объекты в тестах не являются документированной схемой
SourceCraft.

Для текущей проверки источника есть отдельный инструмент разработки
`scripts/probe_sourcecraft_appsec.py`. Он использует уже авторизованный локальный
`src` CLI и выполняет только чтение. Для SAST, SCA и secret scanning инструмент
выводит безопасную сводку: доступность, число элементов в выборке не более 100 и
список уровней критичности. Сырые finding'и, фрагменты кода, токены, stderr CLI и
имя приватного репозитория в вывод не попадают. Это зонд доступности, а не
production-поставщик и не оценка безопасности:

```sh
python scripts/probe_sourcecraft_appsec.py owner/repository --src-bin /path/to/src
```

Если SourceCraft вернёт `null`, зонд сообщит `unavailable`, а не ноль findings.
Контролируемая проверка уже подтвердила непустой SAST-ответ на уровне безопасной
сводки: доступность, число элементов ограниченной выборки и уровни критичности.
Она не подтверждает полноту списка, связь finding'ов с конкретным коммитом или
схему каждого finding'а. Поэтому следующим этапом остаются постраничный
production-поставщик с минимальными правами и согласованная методика score.

## Адаптация CLI-сводки к SecurityFacts

Модуль `backend/app/integrations/sourcecraft_appsec_facts.py` связывает
безопасный CLI-зонд с `security.make_analyzer`. Он принимает ровно по одной
сводке `SAST`, `SCA` и `SECRETS` и детерминированно упорядочивает их.
Дубликат, пропущенный движок или неверный тип результата становятся
фиксированной ошибкой маппинга без содержимого ответа.

| Сводки движков | SecurityFacts | Итог анализатора |
| --- | --- | --- |
| Хотя бы один `available` | безопасный агрегат трёх движков | `insufficient_sample`, без score |
| Все три `unavailable` | `payload=None` | `unavailable`, не ноль findings |
| Нет `available`, есть `error` | безопасный `source_error` | `error`, без score |
| Неполный или дублированный набор | ошибка маппинга | `error`, без score |

`finding_count` ограничен диапазоном `0..100`. Это размер CLI-выборки,
а не утверждение о полном числе дефектов. Встроенная справка установленного
CLI `0.0.103` показывает `--limit`, но не отдельный флаг пагинации для
`appsec defect list`. Поэтому полнота ответа остаётся непроверенной.

Этот адаптер сам по себе не делает локальную IAM-сессию production-авторизацией
и не подключается к web-сервису автоматически. Для production по-прежнему нужны
минимальные права, явная конфигурация и проверенная полнота выборки.

## Защита данных

В `CategoryResult`, JSON и Markdown попадают только фиксированные статусы, причины
и метрика `appsec_data_availability`. Содержимое findings, фрагменты кода, значения
секретов и исходный текст ошибки в результат не копируются.

`repr(SecurityFacts)` скрывает сырые поля. Исключение поставщика обрабатывается
внутри фабрики с фиксированным сообщением в журнале, без текста исключения и traceback.
Остановка процесса и отмена выполнения не подавляются.

Это защита выходов данного модуля: сырые данные остаются в памяти `SecurityFacts`.
Будущий поставщик также должен исключать чувствительные данные из своих журналов;
сырой объект нельзя отдельно сериализовать в отчёт или логировать его поля.

## Воспроизводимая проверка

```sh
python -m pytest backend/tests/test_security_analyzer.py backend/tests/test_security_reporting.py backend/tests/test_sourcecraft_fixtures.py backend/tests/test_sourcecraft_appsec_probe.py backend/tests/test_sourcecraft_appsec_facts.py -q
```

Проверяются валидация входов, отсутствие выдуманных баллов, ошибки поставщика,
отмена, повторные вызовы для разных репозиториев и скрытие сырых данных в `repr`.
Сквозные тесты проходят через общий runner, расчёт Score, хранилище в памяти
и HTTP-выдачу JSON/Markdown. Используются обезличенный fixture `null`, синтетические
маркеры и локальный ASGI-транспорт без запросов к SourceCraft.
