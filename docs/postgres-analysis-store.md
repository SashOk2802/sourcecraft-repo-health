# PostgreSQL: снимки анализов

## Назначение

Каждый завершённый запуск анализа сохраняется как неизменяемый снимок. Это позволяет
открывать один и тот же отчёт после перезапуска backend и не пересчитывать Score при
каждом запросе frontend.

## Таблица

PostgreSQL-хранилище создаёт таблицу analysis_snapshots со следующими полями:

| Поле | Содержание |
| --- | --- |
| analysis_id | Стабильный идентификатор запуска, первичный ключ |
| payload | Полный JSONB-снимок результата runner: контекст, категории, метрики, рекомендации и Score |
| report | Готовая JSON-модель, которую возвращает endpoint отчёта |
| markdown | Markdown-версия того же отчёта |
| created_at | Время сохранения снимка |

Повторное сохранение с тем же analysis_id запрещено. Для повторной проверки
репозитория создаётся новый идентификатор анализа.

## Подключение

Backend выбирает PostgresAnalysisStore, если задана переменная DATABASE_URL. Строка
подключения из compose использует драйвер SQLAlchemy-стиля
postgresql+asyncpg://; хранилище преобразует её в формат, который принимает asyncpg.

Без DATABASE_URL backend использует InMemoryAnalysisStore. Это режим для
изолированных HTTP-тестов и он не предназначен для запуска приложения.

## Жизненный цикл

При старте FastAPI открывает пул PostgreSQL и создаёт таблицу, если её ещё нет.
При остановке приложения пул закрывается. Чтение готового отчёта берёт сохранённые
report и markdown, поэтому не запускает анализаторы и не пересчитывает метрику.

Автоматическое создание таблицы — решение для MVP. Перед первым production-развёртыванием
нужно заменить его миграциями Alembic: зафиксировать начальную схему и все последующие
изменения структуры базы.
