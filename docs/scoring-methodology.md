# Методика Repo Health Score v2

Этот документ фиксирует, как факты превращаются в оценки. Он нужен команде, ревьюеру и экрану «Как считаем»: без него категория формально не готова.

Источник правды для уже реализованных правил — код. Если текст и код расходятся, править нужно документ после изменения кода, а не наоборот.

| Раздел | Реализация |
| --- | --- |
| Итоговый Score | `backend/app/scoring/engine.py` |
| Категория Issues | `backend/app/analyzers/issues.py` |
| Категория Activity | `backend/app/analyzers/activity.py` |
| Общие статусы и контракты | `backend/app/contracts.py` |

Версия методики: **v2**.

v1 измеряла Activity без недель коммитов. v2 добавляет `active_weeks_in_period` с сырым весом 25. Это несовместимое изменение формулы категории: снимок v2 не ставится в один рейтинг со снимком v1, даже если в конкретном запуске история коммитов не прочиталась. Веса шести категорий не менялись.

## 1. Общие правила

1. Каждая категория возвращает оценку **0–100** или `null` вместе со статусом данных.
2. Отсутствие данных **не равно** нулю баллов.
3. Score считается только по категориям со статусом `measured`. Веса остальных не участвуют в знаменателе.
4. Категория `not_applicable` исключается и из Score, и из покрытия.
5. Score **не умножается** на Coverage: низкое покрытие помечает оценку как предварительную, но не штрафует число.
6. Промежуточные значения не округляются; в интерфейсе округляется только отображение.

### Веса категорий

| Код | Категория | Вес |
| --- | --- | ---: |
| `security` | Безопасность | 25% |
| `cicd` | CI/CD | 20% |
| `documentation` | Документация | 20% |
| `activity` | Активность | 15% |
| `issues` | Issues | 15% |
| `code_health` | Состояние кода | 5% |

### Статусы данных

| Статус | Смысл | Score категории |
| --- | --- | --- |
| `measured` | Есть хотя бы одна применимая метрика | 0–100 |
| `unavailable` | Источник недоступен или оба списка задач не получены | `null` |
| `not_applicable` | Категория к репозиторию не относится | `null` |
| `insufficient_sample` | Данные есть, но выборка недостаточна или оборвана | `null` |
| `error` | Внутренняя ошибка анализа | `null` |

### Формула Score

Для измеренных категорий:

```text
Score_base = sum(w_i * Category_i) / sum(w_i)
```

где `w_i` — вес категории из таблицы выше, `Category_i` — оценка категории.

Coverage:

```text
Coverage = measured_weight / applicable_weight
```

`applicable_weight` — сумма весов всех категорий, кроме `not_applicable`.
`measured_weight` — сумма весов категорий со статусом `measured`.
При `Coverage < 1` итог помечается как предварительный (`is_preliminary`).

Ограничение при подтверждённой открытой критической AppSec-уязвимости:

```text
Score = min(Score_base, 60)
```

Ограничение не применяется, если Security не измерена, AppSec недоступен, finding ложный или уже исправлен.

## 2. Категория Issues

Цель категории — оценить, **как проект отвечает на обращения**, а не сколько задач открыто. У популярного репозитория открытых задач всегда больше; само число ни о чём не говорит.

Модуль разделён на `collect` и `evaluate`:

- `collect` ходит в SourceCraft и возвращает факты;
- `evaluate` — чистая функция: без сети и без системного времени. Момент анализа и период приходят во входном `AnalysisContext`.

Контрольный период в живом прогоне и в фикстурных тестах — **180 дней** до `analyzed_at`. Это параметр запуска, а не константа внутри формулы метрик.

### 2.1. Сбор данных

Запросы идут к:

```text
GET /repos/{org}/{repo}/issues?filter=status=...
```

| Группа | Фильтры API | Зачем |
| --- | --- | --- |
| Открытые | `open`, `in_progress` | Задачи в работе — ещё открытый трекер, не решённые |
| Закрытые | `closed` | Решённые и отменённые |

Правила сбора:

1. Группы запрашиваются независимо. Ошибка одной не обнуляет другую.
2. Внутри группы ошибка одного фильтра не затирает успешные ответы остальных.
3. Пересечение `open` и `in_progress` убирается по `id`, иначе по `slug`.
4. Org и repo в пути URL кодируются.
5. Страница: до **100** задач; бюджет по умолчанию — **30** страниц на фильтр. Если токен следующей страницы ещё есть после лимита, выборка помечается как `truncated`. Повтор того же `next_page_token` — ошибка этого фильтра, а не следующая страница.
6. Запись без `created_at` или `updated_at` пропускается и учитывается в `skipped_count`.

Дата выхода из открытого состояния:

```text
closed_at = completed_at, если есть, иначе updated_at
```

У части репозиториев после миграции с GitHub `completed_at` пуст. Пустая дата **не** считается «закрыто в ноль».

Решённой считается только задача со `status_type = completed`. Отменённые (`cancelled`) в «решённые» не входят: иначе оценку можно поднять, массово отменяя задачи.

### 2.2. Метрики

Внутри категории веса нормируются по **доступным** метрикам, как веса категорий в ядре Score.

| Код | Смысл | Вес | Когда метрика выпадает |
| --- | --- | ---: | --- |
| `stale_open_ratio` | Доля брошенных открытых задач | 45% | Нет открытого списка, он оборван или открытых задач нет |
| `backlog_trend` | Решено / создано за период | 30% | Недоступен или оборван любой из списков; за период не создано ни одной задачи |
| `median_days_to_close` | Медиана дней до решения | 25% | Закрытый список недоступен или оборван; меньше **3** решённых в периоде |

Нормализация — линейная между «хорошо» и «плохо», результат ограничен диапазоном 0–100:

```text
score = clamp((value - worst) / (best - worst), 0, 1) * 100
```

#### `stale_open_ratio`

```text
stale = открытые задачи, у которых (analyzed_at - updated_at) > 90 дней
ratio = |stale| / |open_issues|
```

| Параметр | Значение |
| --- | ---: |
| Порог «брошена» | 90 дней |
| Лучший ratio | 0.05 → 100 |
| Худший ratio | 0.50 → 0 |

В evidence попадают до пяти самых старых брошенных задач со ссылкой `{web_url}/issues/{slug}`, если `web_url` известен.

#### `backlog_trend`

```text
created  = задачи (open ∪ closed), созданные в [period_start, period_end]
resolved = closed ∩ completed, у которых closed_at в периоде
ratio    = |resolved| / |created|
```

Для нормализации используется `min(ratio, 1.0)`: разбор быстрее поступления не даёт больше 100 баллов.

| Параметр | Значение |
| --- | ---: |
| Лучший ratio | 1.0 → 100 |
| Худший ratio | 0.25 → 0 |

Отменённые в периоде в числитель не входят, но упоминаются в summary.

#### `median_days_to_close`

Берутся решённые задачи с `closed_at` в периоде. Для каждой считается:

```text
days = (closed_at - created_at) в днях
value = median(days)
```

| Параметр | Значение |
| --- | ---: |
| Минимальная выборка | 3 задачи |
| Лучшая медиана | 7 дней → 100 |
| Худшая медиана | 180 дней → 0 |

### 2.3. Оценка категории

```text
Issues = sum(a_j * Metric_j) / sum(a_j)
```

где суммируются только измеренные метрики, `a_j` — веса из таблицы выше.

Если ни одна метрика не измерилась, score = `null`, статус выбирается так:

| Условие | Статус |
| --- | --- |
| Ошибки по обоим спискам | `unavailable` |
| Оба списка доступны, задач 0, skipped = 0 | `not_applicable` |
| Есть задачи, но все без обязательных дат | `insufficient_sample` |
| Выборка оборвана (`truncated`) | `insufficient_sample` |
| Иначе нет применимых метрик | `insufficient_sample` |

### 2.4. Рекомендации

Рекомендации строятся только по измеренным метрикам.

| Код | Приоритет | Условие | Смысл |
| --- | --- | --- | --- |
| `issues-triage-stale` | P1 | `stale_open_ratio > 0.2` | Разобрать брошенные задачи |
| `issues-backlog-growing` | P2 | `backlog_trend < 0.5` | Очередь растёт быстрее разбора |
| `issues-aging-watch` | P3 | Есть задачи возрастом 30–90 дней **и** нет P1/P2 | Не дать задачам стать брошенными |

У `issues-triage-stale` и `issues-backlog-growing` есть ссылки на факты: до пяти самых старых брошенных задач и до пяти созданных за период, которые ещё открыты. Решённые и отменённые в эти ссылки не входят. `expected_score_delta` считается повторным прогоном формулы категории. Для брошенных задач сценарий — обновить перечисленные в рекомендации. Для бэклога — довести `resolved / created` до 1.0. Наблюдение за задачами 30–90 дней числовой дельты не даёт: пока они не стали брошенными, формула не меняется.

## 3. Категория Activity

Цель категории — понять, **развивается ли проект**, а не насколько он «громкий». ТЗ предлагает коммиты, частоту, дату последней активности, contributors, MR, релизы и динамику.

Ограничения, проверенные по API и git:

- REST API коммитов у SourceCraft нет. Частота считается по истории SHA, зафиксированного на старте анализа: отдельный shallow-клон `--shallow-since` за период, без файлов (`--filter=blob:none`, `--no-checkout`) и без углубления рабочего клона документации. `git log` идёт от этого SHA, а не от HEAD на момент клона.
- В оценку входит число **недель** с коммитами, не число коммитов. Потолок — 8 недель за период.
- Если история не запрашивалась, недоступна или оборвана бюджетом в 20 000 коммитов, метрика выпадает. Уже посчитанные API-метрики и их веса не меняются.
- Список contributors — это люди, без числа коммитов.
- Лайки и `rating` в Score не входят.
- Сырой объём MR и релизов ограничен потолком: три недавних merge дают тот же вклад, что и семьдесят. Это устойчивость формулы (обязательная часть ТЗ), а не детектор накрутки рейтинга (звёздочка).

`collect` и `evaluate` разделены так же, как у Issues. Период в фикстурах — 180 дней.

### 3.1. Сбор данных

| Источник | Метод | Что берём |
| --- | --- | --- |
| Репозиторий | `GET /repos/{org}/{repo}` | `last_updated`, `is_empty` |
| Contributors | `GET /repos/{org}/{repo}/contributors` | список участников |
| MR | `GET /repos/{org}/{repo}/pulls` | статус, `created_at`, `updated_at` |
| Релизы | `GET /repos/{org}/{repo}/releases` | `released_at` или `created_at`, `status` |
| История коммитов | `git log <commit_sha>` за период | дата коммита (`%cI`) |

Источники запрашиваются независимо. Org и repo в пути кодируются. Страница до 100 записей, бюджет 30 страниц. Повтор того же `next_page_token` — ошибка этого списка, а не следующая страница. Общий `get_paginated_objects` здесь не используется: при исчерпании бюджета он бросает ошибку, а категории нужен признак `truncated`.

Смерженным считается MR со `status = merged`. Отдельного `merged_at` в ответах нет — для попадания в период используется `updated_at`. Релиз учитывается при `status = published`.

Пустой репозиторий (`is_empty`) → вся категория `not_applicable`.

### 3.2. Метрики

Веса нормируются по доступным метрикам. Нет MR в проекте — метрика MR выпадает, это не ноль баллов.

| Код | Смысл | Вес | Когда выпадает |
| --- | --- | ---: | --- |
| `last_activity_days` | Дней с `last_updated` | 40 | Нет метаданных репозитория |
| `active_weeks_in_period` | Недель периода с хотя бы одним коммитом, **потолок 8** | 25 | История не запрашивалась, недоступна или оборвана |
| `merged_mr_in_period` | Число смерженных MR за период, **потолок 3** | 25 | Список MR недоступен, оборван или пуст |
| `releases_in_period` | Опубликованные релизы за период, **потолок 3** | 20 | Список релизов недоступен, оборван или пуст |
| `contributor_count` | Число участников, **потолок 3** | 15 | Список недоступен, оборван или пуст |

Числа в колонке «Вес» — сырые веса до нормировки. Если история не прочитана, `active_weeks_in_period` выпадает, и относительные веса оставшихся четырёх метрик совпадают с v1. Когда метрика входит в оценку, Score категории уже другой. Поэтому методика целиком — v2, а не «v1, пока git молчит».

Нормализация линейная, как в Issues.

#### `last_activity_days`

| Параметр | Значение |
| --- | ---: |
| Лучшее | 14 дней → 100 |
| Худшее | 180 дней → 0 |

Это дата последней активности репозитория из каталога, не дата последнего коммита.

#### `active_weeks_in_period`

```text
value = число разных ISO-недель (UTC), в которые попал хотя бы один коммит периода
score = linear(min(value, 8), best=8, worst=0)
```

Коммиты вне `[period_start, period_end]` не считаются. Ноль коммитов в успешно прочитанной истории — измеренный 0, а не отсутствие метрики. Два коммита одной недели дают одну неделю. История читается от SHA, записанного в контекст запуска, отдельно от `--depth 1` клона файловых анализаторов. Ошибка, общий таймаут 90 секунд на клон и `git log`, или больше 20 000 коммитов выбрасывают только эту метрику.

#### `merged_mr_in_period`

```text
value = |merged MR с updated_at в периоде|
score = linear(min(value, 3), best=3, worst=0)
```

Пустой список MR → метрика не участвует (прямой push без MR-процесса). Список есть, но merge за период 0 → оценка метрики 0.

#### `releases_in_period`

Аналогично, потолок 3. Нет ни одного релиза в истории → метрика не участвует (не все проекты публикуют GitHub-подобные releases; теги через этот API не подменяются).

#### `contributor_count`

```text
score = linear(min(count, 3), best=3, worst=0)
```

Пустой список не даёт метрику со значением 0: иначе `evaluate` без фактов получал бы `measured` и score 0. Один участник не обнуляет категорию: bus factor — функция со звёздочкой, не Activity.

### 3.3. Рекомендации

| Код | Приоритет | Условие |
| --- | --- | --- |
| `activity-stale-repository` | P1 | `last_activity_days > 90` |
| `activity-mr-not-merged` | P2 | MR есть, за период смержено 0 |
| `activity-no-commits-in-period` | P2 | История прочитана, недель с коммитами 0, и нет P1 |
| `activity-no-recent-release` | P3 | Релизы в истории есть, за период 0, и нет P1/P2 |

`expected_score_delta` — повторный прогон формулы категории. Свежая давность считается как 14 дней (100 баллов метрики). Один смерженный MR и один опубликованный релиз поднимают свою метрику с нуля, не превышая потолок 3. Восемь недель с коммитами поднимают метрику недель до 100. У рекомендации про релизы есть ссылка на последний опубликованный релиз, если он известен.

### 4.1. CI/CD

Категория измеряет не скорость и не число запусков, а надёжность автоматической
проверки изменений. В выборку за `AnalysisContext.period_start` —
`AnalysisContext.period_end` попадают только SourceCraft-запуски с событиями
`push`, `pr_update` или `schedule`. Ручной запуск и restart исключаются: ими
нельзя надёжно измерить обычный путь изменения кода.

Тип `repository_event` распознаётся как допустимый, но также исключён из
расчёта и минимальной выборки. Его наличие не делает остальную историю
недоступной. Включение таких запусков в Score требует отдельного решения о том,
какие события репозитория отражают регулярную проверку кода.

Учитываются только два завершённых исхода:

| Статус запуска | Учитывается как |
| --- | --- |
| `success` | успешный |
| `failed`, `timeout` | неуспешный |
| `created`, `prepared`, `processing`, `awaiting_approval` | ещё без итога, не учитывается |
| `canceled`, `rejected`, `skipped` | не равен сбою CI, не учитывается |

Время выборки — `created_at` запуска. Оно доступно даже если отдельное время
фактического завершения отсутствует или имеет некорректное историческое значение.
Идентификатором запуска служит SourceCraft `slug`: наблюдённый API-ответ может
содержать пустое поле `id`.

```text
CI/CD score = successful_automated_outcome_runs / all_automated_outcome_runs * 100
```

Для измеренной оценки требуется минимум **5** автоматических запусков с итогом.
Итог содержит метрики `automated_ci_outcome_runs` и
`automated_ci_success_rate`; обе опираются на одну и ту же полную выборку.

| Условие | Статус | Причина |
| --- | --- | --- |
| Источник недоступен или поставщик завершился ошибкой | `unavailable` | `cicd_runs_unavailable` |
| История прочитана не полностью | `insufficient_sample` | `cicd_runs_truncated` |
| История доступна, но запусков нет | `insufficient_sample` | `cicd_no_runs` |
| Нет автоматических запусков в периоде | `insufficient_sample` | `cicd_no_automated_runs_in_period` |
| Меньше 5 запусков с итогом | `insufficient_sample` | `cicd_too_few_outcome_runs` |

Пустая история не означает, что CI неприменим: наличие конфигурации и причины
отсутствия запусков собираются отдельным шагом. Неполная пагинация никогда не
превращается в процент успешности. Статусы и тексты source-ошибок не выводятся
в отчёт.

Если есть хотя бы один неуспешный учтённый запуск, выводится рекомендация
разобрать повторяющиеся падения. При успешности ниже 80 % её приоритет `P1`,
иначе `P2`. Рекомендация не заявляет, какой workflow или job сломался: такие
детали требуют отдельной подтверждённой схемы данных и безопасной политики
вывода.

### 4.2. Security

Security-анализатор пока нормализует доступность AppSec-данных. Числовая
формула SAST, SCA и secret scanning появится только после подтверждённой схемы
findings, полноты выборки и политики обработки чувствительных деталей.

### 4.3. Code health — плотность технического долга

<!-- PENDING_APPROVAL: awaiting methodology owner sign-off -->
| Константа | Значение |
| --- | ---: |
| Штраф за один FIXME | 5 баллов |
| Штраф за один TODO | 1 балл |
| Нормировка | на `total_files`, масштаб ×100 |
| Порог рекомендации по TODO | `todos > 15` |
| Порог «критичного FIXME» (P1) | `fixmes >= 2`; единичный FIXME — P2 |

```text
penalty = (fixmes * 5 + todos * 1) / total_files * 100
score   = max(0, 100 - penalty)
expected_score_delta = score_после_устранения - score_до
```

<!-- PENDING_APPROVAL: awaiting methodology owner sign-off -->
Правило малых репозиториев (семантика плотности, ревью V.1): штраф растёт как
`1 / total_files`, поэтому одинокий FIXME обнуляет категорию при
`total_files <= 5` (penalty ≥ 100), одинокий TODO — при `total_files = 1`.
Оценка непрерывна (без скачков), и в репозитории обычного размера одинокий
маркер категорию не обнуляет. Поведение зафиксировано регрессионным тестом
`test_code_health_small_repo_single_marker_density_semantics` (кривая
`total_files` 1/3/6/100 при одном FIXME → 0/0/16.67/95); границу эскалации
P1/P2 закрепляет тест `test_code_health_fixme_critical_count_boundary`
(единичный FIXME — P2, от `FIXME_CRITICAL_COUNT` включительно — P1). Тесты
доказывают стабильность поведения, а не корректность самих чисел.

## 5. Как менять методику

1. Меняете порог или вес в коде анализатора или ядра.
2. Обновляете этот документ в том же PR.
3. При несовместимом изменении формулы поднимаете `methodologyVersion` и согласуете с ядром анализа.
4. Контрольные фикстуры и тесты должны оставаться зелёными либо явно обновляться с объяснением.
