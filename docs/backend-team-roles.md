# Распределение ролей backend-команды из четырёх человек

## Цель первого этапа

Собрать один сквозной сценарий: по репозиторию SourceCraft получить факты, оценки по шести категориям, итоговый Repo Health Score, рекомендации и Markdown-отчёт.

Не стоит ждать, пока все категории будут готовы отдельно. Уже в начале проекта общая версия должна запускать хотя бы один настоящий анализатор и возвращать единый результат.

## Роли

| Участник | Основная зона | Задачи первого этапа | Результат |
| --- | --- | --- | --- |
| 1. Анализ файлов | Документация и состояние кода | Работа с Git и деревом файлов; README, лицензия, инструкции запуска и тестирования, CONTRIBUTING, CODEOWNERS; TODO/FIXME | Модули `documentation` и `code_health`, факты, оценки, рекомендации |
| 2. Интеграция SourceCraft | CI/CD и Security | Общий клиент API/CLI, пагинация, обработка ошибок; сбор CI и реальных данных AppSec | Модули `cicd` и `security`, проверенная матрица доступных данных |
| 3. Жизнь проекта | Activity и Issues | Коммиты, contributors, релизы, MR; открытые, закрытые и зависшие issues | Модули `activity` и `issues`, факты, оценки, рекомендации |
| 4. Ядро анализа | Общие контракты, Score, запуск и отчёты | Оркестрация анализаторов, обработка отсутствующих данных, формула Score, объединение рекомендаций, JSON и Markdown | Единый запуск анализа и согласованный итоговый отчёт |

Человек, отвечающий за ядро, регулярно объединяет изменения и разбирает стыки между модулями. Это не вспомогательная роль, а отдельная важная часть backend-разработки.

## Владение общими модулями

Чтобы не дублировать код, заранее закрепите владельцев.

- Участник 1 владеет модулем доступа к Git и файлам. Участник 3 использует его для анализа истории коммитов.
- Участник 2 владеет клиентом SourceCraft API. Участник 3 использует его для issues, MR и contributors.
- Участник 4 владеет общими контрактами, расчётом Score и форматом отчёта. Изменять контракт можно только после согласования с командой.

Владелец не становится единственным человеком, который может менять модуль. Он отвечает за его качество, обратную совместимость и проверку изменений.

## Общий контракт анализатора

До разделения задач команда должна совместно согласовать вход и результат каждого анализатора.

### Вход

```text
Репозиторий
Ветка и commit SHA
Дата анализа
Период, за который считаются временные метрики
Контекст доступа и доступные источники данных
```

### Результат

```json
{
  "category": "cicd",
  "status": "measured",
  "score": 90,
  "metrics": [
    {
      "name": "successful_runs",
      "value": 18,
      "total": 20
    }
  ],
  "evidence": [],
  "recommendations": []
}
```

### Обязательные правила

1. Каждая категория возвращает оценку от 0 до 100 или `null`.
2. Если данных нет, анализатор возвращает `score: null`, статус и понятную причину. Отсутствие данных не равно нулю баллов.
3. Каждый автор описывает формулу: как факты превращаются в оценку категории.
4. Веса категорий и итоговый Score рассчитывает общее ядро.
5. Автор категории формирует рекомендации по своим проблемам; ядро убирает дубли и сортирует рекомендации по приоритету.
6. Каждая рекомендация должна содержать ссылку на подтверждающий факт, если он доступен.

```text
    analysis/

    reports/

```

У каждого анализатора желательно разделить две функции:

```text
collect(...)  → факты
evaluate(...) → оценка категории
```

Это позволяет проверять формулы на подготовленных данных без постоянных запросов к SourceCraft. На демонстрации итог должен строиться из реальных данных SourceCraft.

## Как работать без опыта командной разработки

### Ветки и pull request

Для каждой небольшой задачи:

```text
Задача → отдельная ветка → pull request → проверка другим участником → main
```

- Ветка `main` всегда должна запускаться.
- Одна ветка — одна понятная задача.
- Pull request проверяет хотя бы один другой участник.
- Не копите большие изменения: объединяйте небольшие готовые задачи каждый день или через день.
- Перед изменением общего контракта, структуры базы или формата отчёта сообщайте команде.

### Ежедневная встреча

Достаточно 10–15 минут. Каждый отвечает на три вопроса:

1. Что уже работает в общей версии?
2. Что будет готово следующим?
3. Что блокирует работу и от кого нужна помощь?

В задачнике хватит колонок:

```text
Нужно сделать → В работе → На проверке → Готово
```

На одного человека лучше брать одну основную задачу одновременно.

## Что считать готовой категорией

Категория считается готовой только если она:

1. Получает данные хотя бы одного реального репозитория SourceCraft.
2. Документирует формулу расчёта.
3. Отличает отсутствие данных от плохого результата.
4. Возвращает факты и рекомендации по общему контракту.
5. Проверена на хорошем, проблемном и недоступном наборе данных.
6. Подключена к общему запуску анализа.

Локальная функция, которая только возвращает число, — это промежуточный результат.

## Первый общий рубеж

Цель на старт:

> По адресу одного репозитория SourceCraft получить единый JSON и Markdown-отчёт с категориями, итоговой оценкой, причинами отсутствия данных и рекомендациями.

После этого можно переходить к API, базе данных, авторизации, очередям и расписанию.

## Риск, который нужно проверить в начале

Самая неопределённая зона — получение реальных Security/AppSec-данных и права доступа после авторизации. Участник 2 должен проверить это в первые дни. Если AppSec недоступен через подтверждённый интерфейс, команда должна сразу зафиксировать ограничение и согласовать резервный сценарий, а не обнаружить проблему перед демонстрацией.
