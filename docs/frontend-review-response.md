# Ответ frontend-разработчику

## Общая оценка

Макеты и разделение работы на шесть небольших веток одобряем. Особенно хорошо показаны различия между плохой оценкой, отсутствием данных, ошибкой источника и неприменимостью категории. В отчёте есть объяснение Score, подтверждающие факты, рекомендации и ход анализа.

Открывай PR по одному в порядке: каркас → отчёт → рейтинг → вход и анализ → «Как считаем» → README. После merge предыдущего PR обновляй следующую ветку от свежего main, чтобы не переносить в PR уже принятые изменения.

## 1. Коды категорий

Фиксируем один набор:

~~~text
security
cicd
documentation
activity
issues
code_health
~~~

Категория **dependencies** не используется. Данные о зависимостях и SCA относятся к категории **security**.

## 2. Веса и ограничение Score

Для методики **v1** фиксируем веса:

| Категория | Вес |
| --- | ---: |
| Security | 25% |
| CI/CD | 20% |
| Документация | 20% |
| Активность | 15% |
| Issues | 15% |
| Code health | 5% |

При подтверждённой открытой критической AppSec-уязвимости применяется ограничение:

~~~text
Score = min(Score без ограничения, 60)
~~~

Ограничение не применяется при отсутствии AppSec-данных, недоступности источника, false positive или исправленной уязвимости.

В ответе отчёта передаём **scoreLimit**: null либо объект с полями **value**, **uncappedScore**, **code** и **summary**.

## 3. Контракт API

Предложение берём за основу. Принимаем **weight**, **effectiveWeight**, **points**, **sources** и **expectedScoreDelta**, а также endpoints рейтинга, методики, запуска и опроса анализа.

Правки к контракту:

1. Вместо **categories[].facts** используем единое имя **categories[].evidence**. В интерфейсе блок можно называть «Факты».
2. **points** передаётся backend без раннего округления; frontend округляет только отображение.
3. Эффекты рекомендаций нельзя складывать. Под списком нужна фраза: «Возможные приросты не суммируются: рекомендации могут влиять на одни и те же метрики или снять общее ограничение Score».
4. Отчёт привязан к неизменяемому снимку анализа:

~~~text
GET /api/v1/analyses/{analysisId}/report
GET /api/v1/analyses/{analysisId}/report.md
~~~

В рейтинге и «Моих репозиториях» backend передаёт **analysisId** последнего отчёта.

5. Повторный запуск не должен создавать дубликат: при активном анализе backend возвращает существующий ID.
6. Если кнопка вызывает браузерную печать, называем её «Печать / сохранить PDF».
7. Для категории без данных добавить подпись **«не участвует в расчёте»**: значение «25 → 0» без пояснения выглядит как потеря баллов.

## 4. Яндекс ID и SourceCraft

Яндекс ID подтверждает личность пользователя в нашем сервисе, но не передаёт backend доступ к его репозиториям SourceCraft.

Для первой версии делаем экран **«Подключить SourceCraft»** и подключение PAT:

~~~text
POST /api/v1/connections/sourcecraft
GET /api/v1/connections/sourcecraft
DELETE /api/v1/connections/sourcecraft
~~~

Токен отправляется на backend один раз, проверяется, хранится зашифрованно и никогда не возвращается в браузер.

## 5. Неполные оценки в рейтинге

Одной звёздочки недостаточно: место рядом с полной оценкой выглядит как прямое сравнение. По умолчанию показываем только полные сопоставимые оценки. Предварительные результаты выводим отдельным блоком ниже с пометкой «Предварительные оценки» и без места в рейтинге. Переключатель «Показать предварительные» оставляем.

## 6. Проверка без Docker

Отсутствие Docker на компьютере не блокирует PR. Перед открытием PR запускай:

~~~powershell
npm ci
npm run check
npm run build
~~~

Также прикладывай скриншоты или короткое видео изменённого сценария.

**Я проверю Docker Compose и связку frontend → API → backend перед merge.**

## Распределение задач backend

| Участник | Ответственность |
| --- | --- |
| Ядро анализа | API-контракт, Score, методика, статусы анализа, сериализация отчёта |
| Интеграция SourceCraft | PAT-подключение, доступные пользователю репозитории, CI и AppSec |
| Анализ файлов | Документация и code_health |
| Жизнь проекта | Activity и issues |

Пока backend не реализовал endpoints, интерфейс продолжает работать на mock-данных. После согласования контракта frontend переключается на настоящий API.
